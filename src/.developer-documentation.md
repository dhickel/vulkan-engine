# Engine Internals & Architecture: The Definitive Guide

## 1. Introduction & High-Level Philosophy
This engine is built as a pedagogical and high-performance Vulkan 1.3 renderer. It aims to bridge the gap between "Hello Triangle" tutorials and production-grade game engines like Unreal or Unity. 

### 1.1 Core Architectural Principles
1.  **Explicit over Implicit**: Following Vulkan's philosophy, the engine does not hide synchronization or memory management behind "magic." Every fence wait and memory barrier is intentional.
2.  **Data-Oriented Design (DOD)**: Instead of an Object-Oriented "Mesh" class that owns its own buffers, we use a central `DataCache` that manages flat arrays of data. This maximizes CPU cache hits and simplifies GPU uploads.
3.  **Modern Vulkan (1.3+)**: We strictly use Dynamic Rendering and Synchronization2. This eliminates the legacy "RenderPass/Framebuffer" boilerplate, making the pipeline much more modular and easier for students to reason about.
4.  **Stateless Rendering**: The backend (`VkRender`) aims to be as stateless as possible. Each frame, it receives a `RenderSubmission` which contains everything needed to draw. This makes the engine robust against state leakage between frames.

## 2. Historical Context: The Evolution of Rendering

To understand *why* this engine is built the way it is, a student must understand where we came from.

### 2.1 The Fixed-Function Era (OpenGL 1.0)
In the early days, you told the GPU "here is a triangle" and "here is a light." You had no control over *how* the pixels were colored. This was easy to use but impossible to customize.

### 2.2 The Programmable Era (OpenGL 2.0 / DX9)
"Shaders" were introduced. You could now write small programs (Vertex and Fragment shaders) to decide how geometry was transformed and how pixels were colored. This led to the first "Modern" looking games.

### 2.3 The Low-Overhead Era (Vulkan / DX12)
Drivers became too "smart" and too slow. Vulkan was created to give the developer direct control over the GPU's memory and command queues. 
**Our engine lives here.** We use Vulkan 1.3, which is the "sweet spot" of the API—it keeps the low-level control but removes the most annoying boilerplate via **Dynamic Rendering**.

## 3. The Engine Lifecycle: From Startup to Shutdown

### 3.1 Initialization Logic (`Renderer::new`)
Initialization is a multi-stage process that ensures all hardware requirements are met before the first frame.

1.  **Window Creation**: Uses `winit` to create a cross-platform window. This also determines the initial "Surface" for Vulkan.
2.  **Vulkan Instance & Device**:
    -   **Instance**: The gateway to the Vulkan API. We enable `VK_EXT_debug_utils` for high-quality validation layers.
    -   **Physical Device Selection**: We score GPUs based on their features. A Discrete GPU (dedicated) is always preferred over an Integrated GPU. We check for mandatory features: `dynamic_rendering`, `sync2`, `buffer_device_address`, and `storage_buffer_8bit_storage`.
    -   **Logical Device**: Created with specific queue families. We request a Graphics Queue (for drawing) and a Transfer Queue (for async uploads).
3.  **Memory Management (`vk_mem` & `VkSubAllocator`)**:
    -   The `vk_mem` crate (VMA) is initialized to handle large-scale memory blocks.
    -   `VkSubAllocator` is set up to provide fine-grained control over vertex and uniform data (see Data Layer docs for details).
4.  **Backend Setup**: Initialization of `VkRenderCore`, which owns the swapchain and synchronization primitives (Fences/Semaphores).
5.  **Cache Pre-warming**: The `DataCache` is initialized with "Engine Defaults." These are critical fallback assets (White Texture, Normal Up Map, Error Pink) that guarantee the engine can always draw *something* if a user-provided asset is missing.

### 3.2 The Main Loop (`Renderer::run`)
The engine loop is designed to be extremely tight and responsive.

```text
[ OS Event ] -> [ Input Manager ] -> [ Scene Update ] -> [ Build Submission ] -> [ GPU Execution ]
      ^                                                                                 |
      +------------------------- <Next Frame> ------------------------------------------+
```

## 4. Frame Sequence Diagram (The Life of a Frame)

Understanding the timing of a frame is essential for high-performance graphics.

| Time | CPU Task | GPU Task |
| :--- | :--- | :--- |
| **0ms** | Poll OS events (Mouse/Keys) | (Still finishing previous frame) |
| **2ms** | Update Camera & Object Positions | (Waiting for Command Buffer) |
| **4ms** | **Record Commands**: Geometry, Lights, UI | (Idle / Background Transfers) |
| **6ms** | **Submit** Command Buffer to GPU | **Start Render**: Clear Screen |
| **8ms** | **Start Recording Next Frame** | **Execute**: Draw 5,000 Triangles |
| **12ms** | (CPU can now sleep or do physics) | **Post-Process**: Bloom & UI |
| **16ms** | (Wait for VSync) | **Present**: Flip Image to Screen |

## 5. Data Flow: The Journey of a Mesh

To understand how the engine works, a student should follow a single mesh from disk to screen.

1.  **On Disk**: The mesh exists as a `.gltf` or `.obj` file.
2.  **Import (CPU)**: `Assimp` or `gltf` crate parses the file into `ProceduralMeshData`. This is just raw Rust vectors of positions, normals, etc.
3.  **Caching**: The `AssetManager` receives the raw data. It assigns a `MeshHandle` (a unique ID).
4.  **Staging (CPU-GPU Bridge)**:
    -   The data is copied into a "Host Visible" staging buffer. This is memory that both the CPU and GPU can see.
    -   A `vkCmdCopyBuffer` command is recorded on the Transfer Queue.
5.  **Residency (GPU)**:
    -   The data is moved into "Device Local" memory (the fast VRAM on the graphics card).
    -   The `MeshCache` marks the handle as `Loaded`.
6.  **Rendering**:
    -   In the `GeometryPass`, the renderer sees the `MeshHandle` in the `RenderSubmission`.
    -   It looks up the "Device Address" (a GPU pointer) for that mesh.
    -   The shader uses that address to fetch the vertices and draw them.

## 6. The Modern Rendering Pipeline: Forward PBR

We chose a **Forward PBR** approach for its clarity and balance of performance.

### 6.1 Why Forward?
In a "Deferred" renderer, you draw to many textures (G-Buffers) and then combine them. While powerful, it is very memory-intensive and makes transparency difficult.
**Forward Rendering** draws each object directly to the screen. This allows us to use MSAA (Multi-Sample Anti-Aliasing) easily and simplifies the logic for students.

### 6.2 PBR Logic: The Cook-Torrance Model
Our shaders implement the standard PBR equation. It is broken into three main terms:
1.  **D (Normal Distribution Function)**: Calculates how many microfacets are aligned with the camera. We use Trowbridge-Reitz GGX.
2.  **G (Geometric Shadowing Function)**: Calculates how much the microfacets shadow each other. We use Smith’s Schlick-GGX.
3.  **F (Fresnel Equation)**: Calculates how much light reflects vs. refracts at different angles.

### 6.3 Image-Based Lighting (IBL)
Standard lights (Point/Directional) are "punctual"—they come from a single point. Real-world light comes from everywhere.
-   **Environment Maps**: We pre-process a skybox into two special cubemaps.
-   **Irradiance Map**: Low-frequency light. It tells the shader the "ambient" color of a surface based on which way it is facing.
-   **Pre-filtered Map**: High-frequency specular reflections. It allows us to draw "blurry" reflections on rough surfaces without tracing any rays.

## 7. Advanced Concepts for Students

### 7.1 Vertex Pulling vs. Vertex Input
Most older tutorials use `VkVertexInputBindingDescription`. This is fixed-function hardware.
**We use Vertex Pulling**. We bind our vertex buffer as a `Storage Buffer`. In the vertex shader, we do this:
```glsl
layout(buffer_reference) buffer VertexBuffer { Vertex v[]; };
// ...
Vertex v = vertex_buffer.v[gl_VertexIndex];
```
This is faster on modern GPUs and allows for much more flexible vertex formats (like 8-bit or compressed data).

### 7.2 Synchronization: The "Fence" and the "Semaphore"
Synchronization is the hardest part of Vulkan.
-   **Fences**: Think of a fence like a "Finished" flag. The CPU checks the fence to see if the GPU is done. If the fence isn't signaled, the CPU *waits*.
-   **Semaphores**: These are GPU-only "Stoplights." They coordinate between different GPU tasks (e.g., "Don't start the Geometry Pass until the Swapchain Image is ready").

## 8. Common Pitfalls & "Gotchas"
-   **Resource Leakage**: In Vulkan, if you create a texture, you *must* destroy it. The engine uses "Main Deletion Queues" to automate this, but students must be careful when adding new types of resources.
-   **Validation Errors**: The red text is your friend. 99% of crashes are caught by the validation layers before they happen.
-   **Coordinate Systems**: Vulkan uses a "Y-Down" coordinate system for its NDC space, unlike OpenGL's "Y-Up." We handle this in our projection matrix, but it's a common source of upside-down rendering!

## 9. Student Project Ideas (Learning Exercises)
1.  **Add a Fog Pass**: Modify the Render Graph to add a post-processing pass that colors pixels based on their depth.
2.  **Implement a Simple Animation System**: Use the `SceneNode` hierarchy to make a "swinging door" or a "spinning coin."
3.  **Create a New Material Type**: Write a "Toon" shader (Cell Shading) and integrate it into the `MaterialShadingModel` enum.
4.  **Optimize the Scene Graph**: Implement "Frustum Culling" to skip drawing objects that are behind the camera.
