# Renderer API: The Engine Facade & Orchestration

## 1. Introduction: The Power of a Facade
A modern Vulkan engine is incredibly complex. Initializing a device, managing swapchains, and recording command buffers requires thousands of lines of code. For a game developer, this complexity is a distraction.

The `api` module provides the **Facade**. It wraps the entire engine into a few high-level structs like `Renderer` and `Scene`.
-   **Goal**: Allow a developer to write `renderer.run_frame()` and have everything "just work."
-   **Security**: By hiding the `VkDevice` and `VkInstance`, the API prevents the user from accidentally making invalid Vulkan calls that would crash the driver.

## 2. The `Renderer` Lifecycle: A Detailed Walkthrough

### 2.1 Creation (`Renderer::new`)
When you create a `Renderer`, it performs a "Great Initialization" sequence.

1.  **Context Creation**: It initializes the OS window and the Vulkan Backend.
2.  **System Startup**:
    -   Starts the `InputManager`.
    -   Initializes the `DataCache` (the asset database).
    -   Sets up the `RenderGraph` (the frame "script").
3.  **Bootstrapping**: It loads the "Engine Assets"—textures and shaders that are required for the renderer to function, even if the user's game has no assets yet.

### 2.2 The Frame Update (`Renderer::run_frame`)
This method is called once per tick of your game loop. Here is the nitty-gritty logic:

```rust
pub fn run_frame(&mut self) -> Result<FrameRenderOutcome, RendererFrameError> {
    // 1. Logic Sync
    // We update the input manager so any key presses from the OS are now 
    // available to our listeners (like the camera).
    self.update_input();

    // 2. Scene Preparation
    // We ask the SceneWorld to update its transforms. If the player moved,
    // all their attached equipment and lights move now.
    self.scene.update();

    // 3. Backend Execution
    // This is the "handoff." We build a RenderSubmission (a flat snapshot 
    // of the scene) and send it to the Vulkan backend.
    let submission = self.scene.build_submission();
    self.backend.render(self.frame_count, &submission);

    self.frame_count += 1;
    Ok(FrameRenderOutcome::Success)
}
```

## 3. Asynchronous Asset Loading: The `LoadTicket` System

Loading a 3D model involves reading bytes from a slow disk, decompressing textures, and parsing complex math. We solve this with the **Ticket System**.

### 3.1 The Loading Pipeline (Sequence of events)

1.  **Request**: User calls `renderer.load_mesh("dragon.gltf")`.
2.  **Spawn**: A background thread is spawned (or pulled from a pool).
3.  **Ticket**: The user receives a `LoadTicket` immediately.
4.  **Parse**: The background thread uses `Assimp` to extract vertices and textures.
5.  **GPU Transfer**: The data is sent to the `VkTransfer` system (see Data docs).
6.  **Polling**: The user checks `ticket.poll()`.
7.  **Finalize**: Once finished, `poll()` returns the `MeshHandle`.

### 3.2 Thread Safety in Loading
Asset loading is a "Race Condition" waiting to happen. 
-   **The Solution**: We use `Arc<Mutex<DataCache>>`. 
-   The background thread locks the cache, adds the "Unloaded" asset, and releases the lock. 
-   The main thread (renderer) locks the cache once per frame to check for any new "Loaded" assets to bind.

## 4. Step-by-Step: Adding a New Model to the Scene

To help students, here is the exact code flow to get a model on screen:

```rust
// 1. Start the load
let ticket = renderer.load_model("assets/viking_room.obj");

// 2. In your update loop, wait for it
if let Some(mesh_handle) = ticket.get_handle() {
    // 3. Create a node for it
    let node_id = renderer.scene.add_node(SceneNodeId::ROOT);
    
    // 4. Attach the mesh and a material
    renderer.scene.set_mesh(node_id, mesh_handle);
    renderer.scene.set_material(node_id, my_material_handle);
}
```

## 5. Error Recovery Patterns

In graphics, errors are often "Transient" (they happen once and then go away).

1.  **Swapchain Out of Date**: This happens when you resize the window.
    -   *Recovery*: The `Renderer` catches the `RendererFrameError::OutOfDate` and automatically calls `rebuild_swapchain()`.
2.  **Device Lost**: This happens if the GPU crashes or the driver is updated.
    -   *Recovery*: This is fatal. The API ensures a clean exit so the user doesn't have to force-reboot their PC.
3.  **Missing Assets**:
    -   *Recovery*: Instead of crashing, the API returns a "White Texture" or "Error Pink" material. This allows the developer to keep working even if some files are broken.

## 7. Concepts for Students
-   **The Facade Pattern**: The `Renderer` is a facade. It provides a simple `render()` method that hides 3,000 lines of Vulkan code.
-   **Handles vs. Pointers**: We use `MeshHandle` (an ID) instead of `&Mesh` (a reference). This is safer in Rust because IDs don't have lifetime issues.
-   **RAII (Resource Acquisition Is Initialization)**: When the `Renderer` is dropped, it automatically cleans up all Vulkan resources, images, and buffers in the correct order.

## 9. Performance Considerations for API Users
1.  **Avoid Excessive Node Creation**: While nodes are cheap, creating 100,000 nodes will slow down the hierarchy traversal.
2.  **Batch Your Loads**: Requesting 100 textures at once allows the `AssetManager` to optimize the GPU copy commands.
3.  **Reuse Materials**: Every unique `MaterialHandle` requires a state change on the GPU. If two objects look the same, give them the same handle!
