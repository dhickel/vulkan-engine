# Vulkan Backend: The Low-Level Graphics Driver

## 1. Introduction: Why Vulkan?
Vulkan is a "Close-to-the-Metal" API. Unlike OpenGL or DirectX 11, it does not manage memory or synchronization for you. You are responsible for every byte and every microsecond.
-   **Why use it?**: Maximum performance and total control. It allows us to use all CPU cores to record commands simultaneously.
-   **The Cost**: Massive amounts of "Boilerplate" code. This module handles that boilerplate so the rest of the engine can stay clean.

---

## 2. Step-by-Step Device Initialization (`vk_init.rs`)

Starting a Vulkan engine is like starting a spaceship. You must check every system before you can launch.

### 2.1 The `Instance` & `Entry`
-   **`Entry`**: The loader that finds the Vulkan driver on your OS.
-   **`Instance`**: The connection between your app and the driver. We request specific **Layers** (like `VK_LAYER_KHRONOS_validation`) to help us find bugs.

### 2.2 Physical Device Selection
Not all GPUs are created equal. We look for:
-   **Queue Families**: We need a Graphics queue and a Transfer queue.
-   **Extensions**: Specifically `VK_KHR_swapchain` so we can see the results on a monitor.
-   **Features**: We require `Dynamic Rendering` (Vulkan 1.3) and `Buffer Device Address`.

---

## 3. The Frame Ring Buffer: Hiding Latency

A common mistake in graphics is waiting for the GPU. If you say "GPU, Draw!" and then wait for it to finish, your CPU is sitting idle for 16 milliseconds.

### 3.1 Two Frames in Flight
We use two "Frame" slots (Slot 0 and Slot 1).
-   While the GPU is drawing Slot 0, the CPU is recording Slot 1.
-   In the next frame, they swap roles.
-   This ensures both the CPU and GPU are working at 100% capacity.

---

## 4. Vulkan Descriptor Sets: The Nitty-Gritty

Descriptor sets are how we tell the GPU where our textures and buffers are. 

### 4.1 The Layout
A `DescriptorSetLayout` is like a "Function Signature." It says: "This shader expects one UBO at binding 0 and five Textures at bindings 1-5."

### 4.2 The Pool
You cannot create a descriptor set from nothing. You must allocate it from a `DescriptorPool`. 

---

## 5. Pipeline Barriers: The "10 Commandments" of Synchronization

Barriers are how we tell the GPU that "Pass A is finished, Pass B can start."

1.  **Commandment I**: Thou shalt not read what is currently being written.
2.  **Commandment II**: Thou shalt use `Synchronization 2` whenever possible.
3.  **Commandment III**: Thou shalt transition images to the correct `ImageLayout` before use.
4.  **Commandment IV**: Thou shalt always wait for the `render_fence` before recording a new frame.
5.  **Commandment V**: Thou shalt use the correct `AccessFlags` (e.g., `TRANSFER_READ` vs `SHADER_READ`).

## 6. Detailed Logic: Image-Based Lighting (IBL) Pre-computation

Our PBR renderer needs special textures to provide ambient lighting. We generate these on the GPU at startup.

### 6.1 The Equirectangular to Cubemap Pass
Most skyboxes are flat images. We use a compute shader to project this onto the 6 faces of a cube.

### 6.2 The Irradiance Pass
-   **Goal**: Calculate the "Ambient Diffuse" light.
-   **Logic**: Each pixel in the result is the average of a hemisphere of pixels in the source.

## 7. The 12 Steps of a Swapchain Rebuild

When a user resizes the window, the old "Swapchain" becomes invalid. We must recreate it without crashing.

1.  **Wait**: `vkDeviceWaitIdle` – Ensure the GPU is doing absolutely nothing.
2.  **Check**: Get the new window size from the OS.
3.  **Destroy Old**: Delete the old `VkSwapchain` and its `VkImageView`s.
4.  **Create New**: Call `vkCreateSwapchainKHR` with the new dimensions.
5.  **Images**: Fetch the new set of images from the swapchain.
6.  **Views**: Create a `VkImageView` for every new image.
7.  **Depth Buffer**: Re-allocate the Depth Image to match the new resolution.
8.  **Internal Targets**: Re-allocate any internal HDR or Post-processing images.
9.  **Descriptor Sets**: Update any descriptor sets that point to these new images.
10. **Viewport/Scissor**: Record new `vkCmdSetViewport` commands for the next frame.
11. **Notify**: Tell the `RenderGraph` that the resolution has changed.
12. **Resume**: Signal the CPU to start recording again.

## 8. Vulkan Memory Management in Depth

Vulkan memory is not like regular RAM. It has **Types** and **Heaps**.

### 8.1 Memory Heaps
-   **Device Local**: Fast VRAM on the GPU card.
-   **Host Visible**: Regular RAM on the motherboard that the GPU can also see.

### 8.2 Memory Properties
-   **Coherent**: If the CPU writes to it, the GPU sees the change immediately (no "Flush" needed).
-   **Cached**: The CPU uses a cache for this memory (fast for reading back from the GPU).

**Our Engine Logic**:
-   **Textures/Meshes**: Stored in `DEVICE_LOCAL` for maximum speed.
-   **Staging Buffers**: Stored in `HOST_VISIBLE | HOST_COHERENT` so we can copy data into them easily from Rust.

## 9. GPU Profiling and Optimization

How do we know if the engine is fast?
1.  **`Timestamp Queries`**: We place "Markers" in the command buffer.
2.  **The Bottleneck**:
    -   **CPU Bound**: The CPU takes too long to record commands.
    -   **GPU Bound**: The GPU takes too long to draw pixels.
