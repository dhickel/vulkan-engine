# Data Layer: Memory Management, Caching & GPU Synchronization

## 1. Introduction: The Challenge of Scale
In a modern 3D engine, data is everything. A single scene can contain:
-   **Millions of Vertices** (Gigabytes of raw geometry)
-   **Thousands of Textures** (Gigabytes of image data)
-   **Complex Materials** (Metadata, parameters, and shader links)

Vulkan provides very low-level tools for managing this data, but they are difficult to use correctly. The `data` module provides the high-level systems required to manage this scale efficiently and safely.

---

## 2. Deep Dive: The `VkSubAllocator`

### 2.1 The "Too Many Allocations" Problem
Graphics cards have a strict limit on how many individual memory "blocks" they can track (usually around 4,096). If you try to allocate a separate buffer for every single wall, chair, and character in your game, you will quickly crash the driver.

### 2.2 The Solution: The "Mega Buffer" Strategy
The `VkSubAllocator` solves this by allocating one or two **enormous** `VkBuffer` objects (e.g., 256MB or 512MB each). It then "sub-allocates" tiny pieces of these buffers for individual meshes.

### 2.3 Memory Layout Diagram (The "Parking Lot")

```text
[ BUFFER START ]
| [ Mesh A (10MB) ] | [ Mesh B (20MB) ] | [ FREE (15MB) ] | [ Mesh C (5MB) ] | [ TAIL (200MB) ]
|                   |                   |                 |                  |
0KB               10MB                30MB              45MB               50MB
```

### 2.4 Sub-Allocation Logic & Algorithms

#### 2.4.1 Bump Allocation (The Fast Path)
Initially, the buffer is empty. We have a `buffer_tail` pointer.
-   **Logic**: When a new mesh arrives, we check if there is enough space between the `buffer_tail` and the end of the buffer.
-   **Action**: We "bump" the tail pointer forward and return the previous address.
-   **Complexity**: O(1). This is incredibly fast.

#### 2.4.2 Free-List Management (The Reuse Path)
When a mesh is deleted, we don't move the other meshes (that would be too expensive). Instead, we mark that space as "Free" and add it to a `FreeChunkVec`.

#### 2.4.3 The Coalescing Algorithm
To prevent fragmentation, we must merge adjacent free spots.
```rust
// Logic inside FreeChunkVec::insert
1. Find if a chunk ends exactly where the new chunk starts (front_adj).
2. Find if a chunk starts exactly where the new chunk ends (back_adj).
3. If both exist, merge all three into one giant "Super Chunk."
4. If only one exists, extend that chunk to include the new space.
```

## 3. Detailed Logic: `TextureCache` & Batching

### 3.1 The "Staging Buffer" Bridge
GPU memory (Device Local) is fast but hard for the CPU to write to. Host memory (RAM) is easy for the CPU to write to but slow for the GPU to read from.
We use a **Staging Buffer** (`VkHostBuffer`) as a middleman.

### 3.2 Batching Logic: Throughput vs. Latency
Recording a command and waiting for the GPU is "expensive" (it takes time). 
**Our Batching Strategy**:
-   We don't upload one texture at a time.
-   We fill the staging buffer with as many textures as possible (e.g., up to 128MB).
-   We then issue **one** copy command for the entire batch.
-   This significantly increases the "Throughput" (total MB per second) of the asset loader.

## 4. Vertex Pulling (Programmable Fetch)

Most older tutorials use `VkVertexInputBindingDescription`. This is fixed-function hardware.
**We use Vertex Pulling**. We bind our vertex buffer as a `Storage Buffer`. 
-   **Vertex Shader**: `layout(set = 0, binding = 0) buffer VertexBuffer { Vertex v[]; };`
-   **Advantage**: This allows us to draw any mesh without changing the "Pipeline State." It also lets us perform "Vertex Skinning" (animation) much more efficiently.

---

## 5. Defragmentation: The "Clean-up" (Planned Feature)

Over time, as meshes are loaded and deleted, the "Parking Lot" becomes full of small holes (fragmentation).
-   **The Logic**: If the `FreeChunkVec` contains more than 100 small holes, we trigger a **Defrag**.
-   **The Process**:
    1.  Pause the renderer.
    2.  Allocate a new temporary buffer.
    3.  Copy all "Resident" meshes from the old buffer to the new buffer, removing all holes.
    4.  Update all `MeshHandle` offsets to point to the new locations.
    5.  Destroy the old buffer.

## 7. Concepts for Students
-   **Fragmentation**: Like a hard drive, GPU memory can get messy over time. Our coalescing algorithm is a "mini-defragmenter."
-   **Host-Visible vs. Device-Local**: Host is "Slow but accessible," Device is "Fast but isolated."
-   **SSBO vs UBO**: SSBOs (Storage) can be very large and are read/write. UBOs (Uniform) are small (usually < 64KB) and read-only but slightly faster for the GPU to access.

## 9. Common Pitfalls in Memory Management
1.  **Alignment Errors**: The GPU might expect a struct to be 16-byte aligned. If it's only 4-byte aligned, the GPU will read the wrong data!
2.  **Use-After-Free**: If you delete a mesh but the GPU is still drawing it, you will see "Garbage" or crash the driver. The `VkFenceQueue` is our shield against this.
3.  **VRAM Over-subscription**: If you try to load 10GB of textures onto an 8GB card, the driver will either crash or start using slow System RAM, making your game run at 1 FPS.
