# Scene Management: Hierarchies, Transforms & Flattening

## 1. Introduction: The Spatial World
A game engine must manage thousands of objects in 3D space. These objects aren't just a flat list; they have relationships. A sword is attached to a hand, which is attached to an arm, which is attached to a body. 

The `scene` module provides the **Scene Graph**—a hierarchical structure that makes these relationships easy to manage for developers and efficient for the GPU.

---

## 2. Core Concepts: The `SceneWorld`

### 2.1 The Hierarchy (`SceneNode`)
A `SceneWorld` is a tree of `SceneNode`s. Each node contains:
-   **Stable Identity**: A `SceneNodeId` (unique `u32`) used to find the node.
-   **Relationships**: A parent ID and a list of children IDs.
-   **Transformations**:
    -   `local_transform`: Position, Rotation, and Scale relative to the parent.
    -   `world_transform`: The final position in the global 3D world.

### 2.2 Why a Tree?
If you move a parent node, all its children move with it. This is mathematically handled by **Matrix Multiplication**.
`WorldMatrix = ParentWorldMatrix * ChildLocalMatrix`

---

## 3. Detailed Logic: The Update Cycle

Every frame, before rendering, the `SceneWorld::update()` method is called. This is a critical two-step process.

### Step 1: Recursive Transform Update
We start at the "Root" nodes (nodes with no parent).
1.  **Calculate World Matrix**: For the root, `world_transform = local_transform`.
2.  **Recurse**: For each child of the root:
    `child.world_transform = root.world_transform * child.local_transform`

### Step 2: Extraction & Flattening
The GPU does not understand trees or parent-child relationships. It wants a flat array of matrices and handles. This is the **`RenderSubmission`**.

---

## 4. Skeletal Animation (Skinning) in the Hierarchy

How do we handle a character's arm moving?
1.  **The Skeleton**: A sub-tree of `SceneNode`s. Each node is a "Bone."
2.  **The Update**: When the character's arm moves, we update the `local_transform` of the "Shoulder" bone.
3.  **The Transform**: The update cycle automatically moves the "Elbow" and "Hand" bones.
4.  **The Submission**: We collect the `world_transform` of every bone and send it to the GPU as an array of matrices.
5.  **The Shader**: The vertex shader pulls the bone matrices and "weights" the vertices to follow them.

---

## 5. Frustum Culling: The Math of Speed

Drawing 10,000 objects is slow. We only want to draw what the player sees.

### 5.1 Sphere vs. Frustum Logic
1.  **Bounding Sphere**: Every mesh has a center point `C` and a radius `R`.
2.  **Frustum Planes**: The camera view is defined by 6 planes (Left, Right, Top, Bottom, Near, Far).
3.  **The Test**: For each plane, calculate the distance from center `C` to the plane.
    -   If `distance < -R` for **any** plane, the object is completely outside.
    -   **Result**: Skip the object. 

This simple math (a few dot products) can save 90% of your GPU's work in a complex scene.

---

## 6. Scene Serialization: Saving your World

A game isn't very useful if you can't save your progress.
-   **Logic**: The `SceneWorld` can be "Serialized" into a JSON or Binary format.
-   **The Process**:
    1.  Recursively walk the tree.
    2.  Write down each node's ID, parent ID, and `local_transform`.
    3.  Write down which `MeshHandle` and `MaterialHandle` are attached.
-   **Loading**: To load, you simply read the file and recreate the nodes in the same order.

## 8. Concepts for Students
-   **Stability**: Using IDs instead of pointers makes the system "Crash Proof" against memory movement.
-   **Hierarchy of Motion**: How a complex character (bones) is just a scene graph inside another scene graph.
-   **The Cost of Deep Trees**: A tree that is 100 levels deep is much slower to update than a tree that is 2 levels deep. Keep your hierarchies shallow!

## 9. Coordinate Spaces Summary

| Space | Reference Point | Purpose |
| :--- | :--- | :--- |

| **World** | Map's (0,0,0) | Where the object is in the game. |
