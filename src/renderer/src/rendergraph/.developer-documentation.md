# Render Graph: Modular Frame Orchestration

## 1. Introduction: Why a Graph?
In a simple renderer, your main loop might look like this:
```rust
draw_skybox();
draw_geometry();
draw_ui();
```
This is fine for 3 lines, but a modern engine has dozens of stages: Shadow maps, Bloom, Depth-of-Field, Motion Blur, etc. A **Render Graph** turns these stages into "Nodes."
-   **Modularity**: You can add a "Thermal Vision" pass just by plugging in a new node.
-   **Dependency Management**: The graph knows that Pass B needs the output of Pass A.
-   **Synchronization**: The graph (eventually) handles the complex Vulkan "Barriers" required to move data between passes.

---

## 2. Core Concepts & Data Structures

### 2.1 The `RenderPassNode` Trait
Every stage in the frame is a struct that implements this trait:
```rust
pub trait RenderPassNode {
    // A unique name for profiling (e.g., "MainGeometryPass")
    fn name(&self) -> &'static str;

    // The logic: Here we record the actual Vulkan commands.
    fn execute(&self, ctx: &mut RenderGraphContext) -> Result<(), String>;
}
```

### 2.2 The `RenderGraphContext`
This is the "Shared Knowledge" passed to every node.
-   **`frame`**: Access to the current command buffer and per-frame descriptor sets.
-   **`submission`**: The list of objects and lights to draw.
-   **`renderer`**: The low-level `VkRenderCore` for accessing caches and device limits.

## 3. The Standard Pipeline: A Pass-by-Pass Deep Dive

### 3.1 `PrepareTargetsPass` (The Traffic Cop)
This is the most critical pass for Vulkan stability. 
-   **Logic**: At the start of the frame, the "Swapchain Image" is in an `UNDEFINED` state. We cannot draw to it yet.
-   **Action**: This pass records an `ImageMemoryBarrier`. It tells the GPU: "Transition the swapchain image to `COLOR_ATTACHMENT_OPTIMAL` and the depth image to `DEPTH_ATTACHMENT_OPTIMAL`."

### 3.2 `SkyboxPass` (The Background)
-   **Logic**: Before we draw the walls and floors, we draw the sky.
-   **Nitty-Gritty**:
    -   We bind a specialized "Skybox Pipeline."
    -   We draw a cube that is centered on the camera.
    -   **Depth Logic**: We disable depth writing. This ensures that the sky is always "behind" everything else.

### 3.3 `GeometryPass` (The Heavy Lifting)
This is where the `RenderSubmission` is actually consumed.

1.  **Bucketing**: We don't just draw objects in a random order. We group them by their **Alpha Mode**:
    -   **Opaque**: Drawn first. They block everything behind them.
    -   **Mask**: Drawn with the opaque pass. These are "binary" transparency.
    -   **Blend**: Drawn last. They must be sorted back-to-front.

## 4. Resource Aliasing (Advanced Logic)

In a traditional renderer, if Pass A needs a temporary 4K image and Pass B needs a temporary 4K image, you allocate 2 images. 
**With a Render Graph**:
1.  The graph tracks when an image is "Last Used."
2.  Once Pass A is finished, the memory for its image can be **reused** (aliased) by Pass B.
3.  This can reduce the VRAM usage of a post-processing pipeline by 50% or more.

---

## 5. Multipass Techniques: Shadow Mapping Logic

To add shadows to the engine, we would add a `ShadowPass` to the graph:
1.  **Node 1 (ShadowPass)**: 
    -   Renders the scene from the *light's* perspective.
    -   Only records depth data to a `ShadowMap` texture.
2.  **Node 2 (GeometryPass)**:
    -   Reads the `ShadowMap` texture from Node 1.
    -   For every pixel, it checks: "Is this pixel farther from the light than the value in the ShadowMap?"
    -   If yes, the pixel is in shadow.

The Render Graph ensures that Node 1 always finishes before Node 2 starts.

## 6. Understanding the "Frame Budget"

To run at 60 FPS, the entire graph must execute in under **16.6ms**.
-   **G-Pass Budget**: Usually 8-10ms (The bulk of the work).
-   **Post-Process Budget**: 2-3ms (Bloom, Fog, Tonemapping).
-   **UI Budget**: 1ms (Imgui).
-   **Sync Overhead**: 0.5ms (The cost of the Render Graph itself).

By measuring the `execute()` time of each node, students can find where the "Bottlenecks" are in their rendering code.

## 7. Student Exercises (Learning Exercises)

1.  **Exercise: Greyscale Pass**: Create a new pass that runs at the very end. It should read the final color image and use a simple shader to remove all color.
2.  **Exercise: Pass Reordering**: Try moving the `SkyboxPass` to run *after* the `GeometryPass`. (Hint: You'll need to use the Depth Buffer to ensure the sky doesn't draw over the objects). This is called "Late-Z" skybox rendering.
3.  **Exercise: Depth Debugger**: Create a pass that visualizes the Depth Buffer as a black-and-white image (Close = White, Far = Black).
4.  **Exercise: Bloom Effect**: (Advanced) Research the "Gaussian Blur" algorithm and try to implement a multi-node Bloom pipeline.

## 8. Concepts for Students
-   **Topological Sort**: A graph can automatically determine the order of passes based on their dependencies.
-   **Memory Aliasing**: Reusing the same memory for different images in different passes to save VRAM.
-   **Dynamic Rendering**: How modern Vulkan removes the need for `VkRenderPass` objects by specifying attachments at command-record time.

## 9. System Diagram: Frame Lifecycle

```text
[ Start Frame ]
      |
      v
[ Prepare Targets ] --- (Barrier: Undefined -> Color Attachment)
      |
      v
[ Skybox Pass ] ------- (Draw background)
      |
      v
[ Geometry Pass ] ----- (Draw Opaque -> Mask -> Blend)
      |
      v
[ Present Copy ] ------ (Barrier: Color Attachment -> Transfer Src)
      |
      v
[ Imgui Pass ] -------- (Draw UI)
      |
      v
[ End Frame ] --------- (Queue Submit & Present)
```
