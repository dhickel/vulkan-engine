# Input System: Event-Driven Broadcaster Architecture

## 1. Introduction: The Need for Decoupling
In a basic game loop, you might check `if (key_pressed('W')) move_forward()`. While simple, this creates **Tight Coupling**. Your player logic is now stuck to your windowing library. 

Our engine uses a **Broadcaster/Listener** pattern. This means:
1.  The Windowing library (`winit`) collects events.
2.  The `InputManager` categorizes and buffers these events.
3.  Any component that needs input (Camera, Player, UI) "subscribes" to the `InputManager`.
4.  The `InputManager` "broadcasts" the events to all subscribers.

This architecture allows us to add a second camera, a debug console, or a GUI without ever changing the core input collection code.

## 2. Core Components and Data Structures

### 2.1 The `InputManager`
The `InputManager` is the central hub. It maintains lists of listeners for different input types:

```rust
pub struct InputManager {
    // Current frame state
    mouse_delta: (f64, f64),
    scroll_state: f32,
    m_button_states: HashSet<MouseButton>,
    key_states: Vec<(KeyCode, bool)>,
    modifiers: HashSet<winit::event::Modifiers>,

    // Registered listeners (using Rc<RefCell> for shared mutability)
    m_pos_listeners: Vec<Rc<RefCell<dyn MousePosListener>>>,
    m_scroll_listeners: Vec<Rc<RefCell<dyn MouseScrollListener>>>,
    m_button_listeners: Vec<Rc<RefCell<dyn MouseBListener>>>,
    key_state_listener: Vec<Rc<RefCell<dyn KeyboardListener>>>,

    // Priority filter
    listen_filter: Option<ListenFilter>,
}
```

### 2.2 Listener Traits
Listeners are defined by traits. To receive keyboard input, a struct must implement `KeyboardListener`:

```rust
pub trait KeyboardListener {
    // Categorization
    fn listener_type(&self) -> ListenerType; 
    fn listener_id(&self) -> u32;

    // Interest Check: "Do I care about this key?"
    fn listener_for(&self, key: KeyCode) -> bool;

    // The Payload: "Something happened!"
    fn broadcast(&mut self, key: KeyCode, pressed: bool, modifiers: &HashSet<Modifiers>);
}
```

## 3. The Logical Flow of an Input Frame

### Stage 1: Collection (During `winit` Event Loop)
As the user interacts with the OS, `winit` generates events. The `Renderer` (the bridge) feeds these into the `InputManager`:

```rust
// Inside the main event loop
match event {
    WindowEvent::KeyboardInput { input, .. } => {
        input_manager.add_keycode(input.virtual_keycode, input.state == Pressed);
    }
    WindowEvent::CursorMoved { position, .. } => {
        input_manager.update_mouse_pos(calculate_delta(position));
    }
    // ... other events
}
```
**Crucial Note**: At this stage, nothing happens in the game logic. We are only filling the "buckets" inside the `InputManager`.

### Stage 2: The Broadcast (`InputManager::update`)
This is where the magic happens. The engine calls `input_manager.update()` once per frame.

1.  **Iterate Listeners**: The manager loops through `key_state_listener`.
2.  **Apply Filter**: If `listen_filter` is `Some(TypeFilter(Gui))`, any listener that returns `ListenerType::GameInput` is skipped.
3.  **Check Interest**: For each key event in the buffer, it calls `listener.listener_for(key)`.
4.  **Execute Logic**: If interested, it calls `listener.broadcast(...)`. 

### Stage 3: Cleanup
After all listeners are notified, the buffers (`key_states`, `mouse_delta`) are cleared. This prevents the same "Key Pressed" event from firing twice in the next frame.

## 4. Input State Machine Diagram

To help students visualize the state of a key, we can use this ASCII state machine:

```text
    (No Event)         (Key Pressed)        (Still Pressed)
[ UNPRESSED ] ------> [ PRESS_START ] ------> [ HELD ]
      ^                     |                    |
      |               (Key Released)       (Key Released)
      +---------------------+--------------------+
```

-   **PRESS_START**: Fired only in the exact frame the key went down. Useful for "Jump" or "Toggle Light."
-   **HELD**: Fired every frame the key is down. Useful for "Walk" or "Fire Machine Gun."
-   **RELEASE**: Fired once when the key is let go.

## 5. Deep Dive: Shared Mutability with `Rc<RefCell>`

Students often ask: "Why not just use a simple reference `&mut Listener`?"
The answer lies in **Ownership and Lifetimes**.

In a game engine:
-   The `InputManager` needs to *call* the listener.
-   The `SceneWorld` needs to *own* the listener (e.g., the Player).
-   The `GuiSystem` might need to *modify* the listener.

In Rust, you can't have multiple mutable references. `Rc<RefCell<T>>` provides a solution:
-   **`Rc` (Reference Counted)**: Allows multiple "owners." The listener stays alive as long as someone has an `Rc` handle to it.
-   **`RefCell`**: Allows "Interior Mutability." We can borrow a `&mut T` at runtime, even if we only have a shared reference. 

**Warning**: If you call `borrow_mut()` twice on the same `RefCell` in the same scope, the engine will crash with a `panic`. Our input system avoids this by keeping the broadcast calls very shallow.

## 6. Input Filtering Logic: Solving the "Chatbox Problem"

Imagine you are playing a game. You press 'Enter' to open a chatbox. You start typing "WASD". 
**The Problem**: Without filtering, your character would also start walking around while you type!

### How we solve it with `ListenerType`
1.  We categorize listeners:
    -   `ListenerType::Window` (High Priority: Escape, Fullscreen)
    -   `ListenerType::Gui` (Medium Priority: Buttons, Input Fields)
    -   `ListenerType::GameInput` (Low Priority: Player Movement)

2.  When the chatbox is focused, the UI system tells the `InputManager`:
    `input_manager.set_filter(ListenFilter::TypeFilter(ListenerType::Gui))`

3.  During `broadcast`, the manager now ignores anything marked `GameInput`. The player stays still, and the text appears in the box.

## 7. Common Input Bugs (And how to fix them)

1.  **"Sticking" Keys**: If the window loses focus while a key is down, the `KeyReleased` event might never be sent. 
    -   *Fix*: The `InputManager` should listen for `WindowEvent::Focused(false)` and manually clear all pressed keys.
2.  **Jittery Mouse**: Raw mouse deltas can be inconsistent between frames.
    -   *Fix*: Apply a small amount of "Smoothing" (averaging the last 3 frames of deltas).
3.  **Double Jumping**: If you use a `HELD` check for jumping, the player will jump 60 times per second.
    -   *Fix*: Use an internal `was_jump_pressed_last_frame` boolean to only fire the logic on the transition from `Unpressed` to `Pressed`.

## 9. Concepts for Students
-   **Poll vs. Interrupt**: OS events are interrupts; our system turns them into a polled update that happens once per frame.
-   **Relative vs. Absolute**: Camera rotation uses **Relative** movement (how much did the mouse move since last frame?). UI buttons use **Absolute** position (is the cursor *inside* the box at (100, 200)?).
-   **Coordinate Systems**: `winit` uses pixels (0,0 is top-left). Our 3D space uses Normalized Device Coordinates (NDC) or World Space.
