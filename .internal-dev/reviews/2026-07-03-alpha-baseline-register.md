# Alpha Baseline Residual Register

Date: 2026-07-03

## Scope

This register consolidates Sprint 01 baseline residuals from `docs/gap-report.md`, the Phase 01 baseline inventory, the Phase 02 docs drift audit, validation reports, root/package manifests, and targeted live-source inspection. It is a classification artifact, not a product-fix plan.

Allowed statuses:

- `verified_current`: live source/docs confirm the issue still exists.
- `stale_resolved`: old claim is contradicted by live source.
- `unknown_needs_audit`: cannot be verified cheaply during Sprint 01.
- `accepted_alpha_debt`: known limitation is accepted for a future sprint.
- `blocked_validation`: validation or evidence could not run and must be retried.

## Risk Assessment

The old gap report can no longer be used as a raw defect list. Several missing-feature claims are contradicted by live source and are now `stale_resolved`, while support crates/apps are better treated as `accepted_alpha_debt` until specific alpha workflows are validated.

The main remaining risk is overclaiming readiness from existence. Workspace membership and a thin crate are not enough evidence for alpha completeness.

## Recommendations

- Use this register as the routing table for Sprint 01 Phase 04 and later deep-track planning.
- Keep `unknown_needs_audit` items out of current-defect lists until a targeted audit verifies them.
- Require visual/headless capture evidence only when a sprint changes renderer-visible behavior or claims visual readiness.
- Preserve the public docs wording that points to current alpha readiness and this residual classification route instead of reviving the old raw gap list.

## Follow-ups

- Phase 04 should run the compile/test/runtime baseline checks from the validation matrix and update `validation-summary.json`.
- Future track planning should convert accepted alpha debt into scoped sprint acceptance criteria, not broad "make engine alpha-ready" work.
