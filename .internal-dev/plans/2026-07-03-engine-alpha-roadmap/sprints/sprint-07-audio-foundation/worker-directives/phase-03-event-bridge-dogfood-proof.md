# Phase 03 Worker Directive: Event Bridge And Sample/Dogfood Proof

## Objective

Connect audio playback status to engine events and provide a narrow opt-in sample or dogfood proof that references a packaged audio clip and attempts playback only when explicitly requested.

## User-Visible Outcome

A developer can see how packaged audio is referenced from an app path, how playback status becomes `AudioEvent`, and why device-backed playback is reported as optional/host-dependent.

## Editable Targets

- `src/events/src/lib.rs` only if existing `AudioEvent` vocabulary is insufficient
- `src/audio/src/lib.rs` if event mapping helper belongs there and does not create dependency inversion
- `apps/dungeon_dogfood/Cargo.toml`
- `apps/dungeon_dogfood/src/*.rs`
- `apps/dungeon_dogfood/assets/content_pack.toml` or a narrow sample project fixture
- Optional small audio fixture under dogfood/sample assets if license/source is clear or bytes are generated by tests
- `reports/dogfood-audio-proof-debt.md` if proof is deferred
- `reports/phase-03-email.md`

## Forbidden Scope

- Do not make `engine_events` depend on `audio`.
- Do not make normal dogfood startup require an audio device or audio clip.
- Do not rewrite broad gameplay, level generation, renderer integration, or editor behavior.
- Do not add unlicensed third-party audio assets.
- Do not use desktop screenshots.
- Do not touch `.idea/engine.iml` or `.reasonix/`.

## Senior-Engineer Guidance

- Prefer using existing `AudioEvent::{ClipStarted, ClipStopped, ClipFinished, ClipFailed}`.
- Add mapping at the consumer boundary: audio runtime status -> event bus emission. Do not let the event crate know about rodio.
- Make playback opt-in with a flag/env/config so validation can run without speakers.
- If adding a real fixture is awkward, generate a tiny WAV during tests and keep package metadata proof separate from runtime smoke.
- A deferred dogfood proof is acceptable only with a concrete debt artifact and passing core validation.

## Ordered Implementation Steps

1. Inspect `engine_events` audio vocabulary and dogfood event usage.
2. Add tests for audio event emission/mapping using durable `AudioClipId`.
3. Add an opt-in dogfood/sample audio path that:
   - reads or references a packaged audio clip by durable ID;
   - loads/probes the clip through `audio`;
   - attempts playback only when explicitly enabled;
   - emits/logs start/failure/stop/finish where practical.
4. Ensure normal dogfood startup remains unchanged when audio is not enabled.
5. Add or update dogfood/sample content metadata to include the audio clip reference if safe.
6. If proof is too risky, create `reports/dogfood-audio-proof-debt.md` with blockers, future slices, and validation expectations.
7. Run compile/test checks and optional device smoke only if safe and explicitly enabled.
8. Draft `reports/phase-03-email.md`.

## Acceptance Criteria

- Audio playback status can be represented as `AudioEvent` with durable `AudioClipId`.
- No dependency inversion is introduced.
- A sample/dogfood path references packaged audio and either:
  - proves opt-in playback path safely; or
  - records a debt artifact explaining why proof is deferred.
- Normal dogfood validation does not require a physical audio device.
- Device smoke status is reported as skipped/blocked/pass, not hidden.

## Negative Checks

- No mandatory device open on normal dogfood launch.
- No broad dogfood rewrite.
- No unlicensed asset addition.
- No false claim that device smoke proves all platform support.

## Validation Commands

```bash
cargo fmt --check
cargo test -p audio
cargo test -p engine_events
cargo check -p dungeon_dogfood
cargo check
```

If dogfood behavior or tests changed:

```bash
cargo test -p dungeon_dogfood
```

Optional device smoke only if explicitly enabled and a device is available:

```bash
RUST_LOG=debug timeout --signal=INT 60s cargo run -p dungeon_dogfood -- --audio-smoke
```

Use the actual implemented command if different and record it.

## Stop Conditions

- Stop if dogfood proof requires broad app architecture changes.
- Stop if normal runtime would become device-dependent.
- Stop if event vocabulary expansion creates dependency cycles or broad event redesign.

## Do Not Close Unless

- Event mapping/proof is tested or debt is documented.
- Dogfood/sample opt-in behavior is explicit.
- Device-dependent support is not oversold.
- The phase is ready for validator review.
